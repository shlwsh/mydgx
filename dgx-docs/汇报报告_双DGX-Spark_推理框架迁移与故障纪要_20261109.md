# 汇报纪要：双 DGX Spark 推理部署、NIM→vLLM 迁移与已发生故障

> **日期**：2026-11-09  
> **用途**：向厂商 / 接手工程师说明双机集群怎么来的、为什么换推理框架、换完之后又出过哪些问题  
> **范围**：DeepSeek-V4-Flash-0731，2× DGX Spark GB10，TP=2  
> **依据**：`docs/项目说明手册_20260826-2241.md`，以及手册索引中的交接、迁移与故障记录  
> **口径**：只整理已有记录。未在原文写明的驱动小版本、复现次数，不在本文补写。

本文与 `汇报报告_Qwen3.6-NVFP4_SilentHang_英伟达技术沟通_20261109.md` 是两套服务。Qwen3.6 是单机 NVFP4 假死；本文是双机 DeepSeek 的框架迁移和稳定性历史。两边都出现过「健康检查看起来正常、推理实际不可用」，但触发条件不同，不能当成同一个缺陷。

---

## 1. 集群在做什么

两台 DGX Spark（GB10）用张量并行跑一个单机内存放不下的模型。

| 项 | 内容 |
|---|---|
| 模型 | `deepseek-ai/DeepSeek-V4-Flash-0731`，约 155G safetensors / FP8 |
| 并行 | TP=2，每机约一半权重 |
| 互联 | ConnectX-7，RoCE 200Gb 直连；管理网只做 bootstrap 和 API |
| 直连地址 | `192.168.100.10` ↔ `192.168.100.11` |
| 现 Rank0 | 工作站 `cube-f22b`，管理地址 `172.19.50.70`，账号 `winbot` |
| Rank1 | `cube-0137`，`172.19.49.159`，账号 `dgxdeploy` |
| 对外入口 | LiteLLM `172.19.50.70:4000`（主用）；vLLM `:18090` 仅本机 |
| 早期入口 | NIM `:8000`。2026-09-10 起手册注明 NIM 已停用，只作历史回滚记录 |

2026-09-04 用工作站换掉了原 Node0 `cube-fe5e`。光纤改插到工作站，模型与镜像从 Node1 经 200G 直传，不再走原 Node0 的无线拷贝。2026-09-10 工作站有线管理口断开，地址从 `172.19.9.104` 改为无线 `172.19.50.70`。下文 IP 以各次记录当时的地址为准。

数据路径：客户端 → Rank0 API → 双机同步激活（RoCE）→ 返回。第一次请求会做 autotune，冷启动慢，之后才到基线吞吐。

## 2. 为什么从 NIM 迁到 vLLM

这是框架更换的唯一主因，不是为了换而换。

### 2.1 NIM 基线能跑，但长上下文会把进程打崩

当时生产基线：

```text
镜像：nvcr.io/nim/deepseek-ai/deepseek-v4-flash-0731:1.11.0-variant
容器：Node0 deepseek-v4-rank0，Node1 deepseek-v4-rank1
API：:8000/v1
```

短上下文可用。迁移方案里记录的暖机吞吐大约是 1K 19.6 tok/s、8K 21.9 tok/s。约 24K 实际 prompt 可以通过。

P0 出现在更长 prompt：

```text
约 40K prompt → CUDA crash
CUDA error at sparse_mla_sm120_prefill.cu:67: operation not permitted
Fatal Python error: Aborted
scheduler_0 exit -6
```

手册把同一缺陷写成：NIM 1.11.0-variant 在 **大于 32K** 时触发 `sparse_mla_sm120_prefill.cu` CUDA crash。硬件是 GB10 / SM121，崩溃点落在 SM120 的 sparse MLA prefill kernel。官方 NIM 这条路径撑不住当时需要的长上下文。

业务目标因此收成三条，而不是先追 1M 上下文或最高吞吐：

- 40K 通过
- 64K 通过
- 0 次 CUDA crash

### 2.2 迁到哪一版

保留 NIM 容器不删，另起一套 vLLM，端口分开（NIM 8000，vLLM 18090）。

| 项 | 值 |
|---|---|
| 运行时 | `ghcr.io/liquidgravityai/2x-dgx-spark-deepseek-v4-flash-0731`，本地 tag `pinned-676a1c89`（arm64，24.8GB） |
| 软件栈 | vLLM 0.26.1rc0 + dspark.r16 + FlashInfer `1ac6942` + CUDA 13.2；NCCL 2.30.4 |
| 权重 | revision `9e165c30e2704aec5d9d593cce3eebd58bbef1cb`，与 NIM 缓存一致，直接复用 |
| 配方 | commit `8a161c09f1269ee8ea18ba324b4682d0712f4e4a` |
| 关键参数 | `MAX_MODEL_LEN=65536`，TP=2，nnodes=2，prefix caching，DSpark speculative decoding（spec=5） |

不采用「在现有 NIM 上继续调参硬扛 40K」作为主路线。NIM 的失败点在预填 kernel，调 KV 或并发解决不了 `scheduler_0` abort。

### 2.3 迁移当时验收了什么

2026-08-26 迁移报告结论是核心目标达成。

| 检查 | 结果 |
|---|---|
| 分布式 | `world_size=2`，master 在 `192.168.100.10`，推理时 CX-7 有双向流量 |
| 8K～32K | 各 3/3 |
| **40K** | **3/3**，NIM 在这里崩溃 |
| 48K、64K | 各 3/3 |
| 真 64K（61509 tokens） | 3/3；冷 prefill 16.7s，前缀缓存命中后 0.7s（TTFT 改善 95.8%） |
| API / tool / reasoning | `/health`、chat、tool_choice=auto、thinking 开关均通过 |
| 吞吐 | 1K：NIM 19.6 → vLLM **47.3**（2.4x）；8K：21.9 → **43.1**（2.0x）；TTFT 持平 |

当时还没做完的是：30 分钟 / 2 小时 / 8 小时 soak，以及 **128K canary 必须等 64K + 8h soak 通过后再开**。后面 9 月的故障，主要就出在这条还没封口的长上下文和双机链路上。

## 3. 部署期问题（NIM 阶段，框架迁移之前）

这些问题不构成换框架的理由，但双机能跑起来之前都踩过。

| 问题 | 表现 | 处理 |
|---|---|---|
| NGC 中国区 451 | `api.ngc.nvidia.com` 的 manifest 直连被拒 | manifest 走非中国出口代理；权重域名 `xfiles.ngc.nvidia.com` 无地理限制，必须放进 `NO_PROXY`。`NO_PROXY` 里一旦误写 API 域名，manifest 又会 451 |
| manifest 抖动把容器打进重启循环 | 默认重试次数是 0，代理抖一下就退出 | `NIM_MANIFEST_DOWNLOAD_MAX_RETRY_COUNT=300`，间隔 3000ms |
| 缓存权限 | `Permission denied (os error 13)` | NIM 以 `nvs`（uid 1000）运行，缓存目录改为 `1000:1000` |
| 8000 端口被占 | Node0 上 Portainer edge agent 占用 API 端口 | Portainer 只留 9000/9443，禁止再映射 8000 |
| 本机代理单点 | Node0 Clash `7897` 进程状态坏掉，拉镜像和 NGC 失败 | `pkill verge-mihomo`，由 clash-verge-service 拉起。Node1 的 7890 依赖后来已解除 |
| vLLM 镜像不好拿 | ghcr 单连接约 5.7MB/s；并发超过约 16 会把代理打崩；`curl -C -` 在该 CDN 上续传卡死；国内镜像站没有这版；`docker load` 不认 OCI layout | 整层串行下载，约 18MB/s；转成 docker-archive 再 load |

网络验收（迁移前已通过，迁移时禁止重做网络）：RoCE `ib_write_bw` 约 13GB/s；NCCL all_gather 16GB，bus bandwidth 约 22.2GB/s。当时两机 `NCCL_IB_GID_INDEX=3`。

## 4. 迁到 vLLM 之后的故障

按时间。每一条都分开写直接原因，避免收成「vLLM 不稳定」一句话。

### 4.1 2026-09-02：RoCE GID 表漂移，双机建链失败

**现象**

- LiteLLM 进程正常，`/v1/models` 仍 200。
- `chat/completions` 全部 500，`Connection error`。
- vLLM `:18090` 没有监听。Rank0 容器 exit 0；Rank1 容器还在，worker 挂住等对端。

**原因**

链路本身是通的：网卡 200Gb、RDMA `LINK_UP`、直连 ping 小于 1ms。失败在 GID 表。

原先 RoCEv2 IPv4 在 **index 3**，这套配置稳定跑过约 6 天。漂移后 index 3 变空，RoCEv2 IPv4 挪到 **index 4**。环境变量仍是 `NCCL_IB_GID_INDEX=3`，NCCL 读到空 GID：

```text
ibv_modify_qp failed with 61 No data available, on dev rocep1s0f0:1
curr state INIT, next state RTR, local GID index 3, local GID ::, remote GID ::
NCCL error: unhandled system error
```

同一天更早的 `sample_tokens` RPC 超时、`EngineDeadError`、进程干净退出，记录里视为这次空 GID 的可信诱因。容器 `restart=no`，退出后不会自己起来。

**处理**

`ib_write_bw -x 4` 复测约 13GB/s 后，双机 `.env.canary64` / `.env.canary128` 的 `IB_GID_INDEX` 从 3 改为 4，先 Rank1 后 Rank0 拉起。`:18090/health` 200，网关 chat 通过。

### 4.2 2026-09-02（GID 修好约 1 小时后）：长上下文 cuBLAS 崩溃

**这不是 4.1 的复发。**

```text
CUDA error: CUBLAS_STATUS_INTERNAL_ERROR
cublasGemmEx(... CUDA_R_16BF ... CUBLAS_GEMM_DEFAULT_TENSOR_OP)
→ EngineDeadError → 容器 exit 0
```

时间线：一个 warmup 没覆盖的 Triton kernel 在线 JIT；随后新请求把 GPU KV 打到约 34.7%（约 12.6 万 token，靠近 131072）。大 shape 上 `cublasGemmEx` 内部错误，引擎退出。dmesg 里的 OOM 发生在更早的启动占内存阶段，与这次崩溃不是同一时刻。

记录把这次和迁移时的风险写在一起：sparse MLA / 长上下文 CUDA 崩溃，需要 40K、64K、128K 分档验证；pinned r16 在贴近 128K 时计算路径仍不稳。处置是重启，并建议先不要在 128K 上限上直接压；必要时退回 canary64（`MAX_MODEL_LEN=65536`）。网关侧后来加了 **125K 硬顶**，超限返回 400，避免请求直接打进这个区间。

### 4.3 2026-09-10：管理地址变化，GID 再次只在一侧漂移，watchdog 修错目录

三件事叠在同一次不可用上。

| 层 | 事实 |
|---|---|
| 客户端 | 工作站有线口 `enP7s7` 断开，`172.19.9.104` 失效，现网是无线 `172.19.50.70`。客户端仍指向旧地址 |
| RoCE | 工作站 HCA `rocep1s0f1` 的 RoCEv2 IPv4 仍在 index **3**；Node1 `rocep1s0f0` 又落在 index **4**，配置仍写 3。只有 Node1 会读到空 GID |
| 自愈 | Rank1 已 Exited(137)。watchdog 用 `/home/winbot/...` 去 SSH 重启 Node1，Node1 实际目录是 `/home/dgxdeploy/...`，自愈永远失败 |

处理：客户端改到 `172.19.50.70:4000`；只改 Node1 的 `IB_GID_INDEX=4`；watchdog 增加 `N1_COMPOSE_DIR`。重启后 `world_size=2`，无 `ibv_modify_qp` 报错，端到端 `RELIT_OK`。

GID 漂移因此不是一次性事故。驱动或网卡布局变化后，**两台机器的 index 可以不一致**，不能假设改一次就永久有效。

### 4.4 2026-09-10 晚：大请求把 Rank0 打退出，窗口被放大

**现象**：约 3 分钟内连续 6 次 `chat/completions` 500。Rank0 在 06:01:41 exit 0，运行约 7318 秒；06:04:30 vLLM 才再次就绪。

**原因（记录中的判断）**

- 直接原因与 09-02 相同一类：大请求 `sample_tokens` RPC 超时 → `EngineDeadError` → 干净退出。该 pinned build 的大 prefill 稳定性缺陷。单发 113K 后来又能成功，所以是偶发，不是每次大请求必崩。
- 放大：统一内存只剩约 3～5GiB；watchdog 冷却 600 秒，空窗可到约 10 分钟；`compose down` 会丢掉崩溃容器日志；soak 在 02:30 停了，崩溃从 03:29 才开始被看到。
- 已排除：内核 OOM killer、GPU Xid、本次的 GID/NCCL、125K 硬顶（超限是 400，不是 500）。

**已落地**

- 重启前先把 `docker logs` 存到 `~/logs/vllm-crash-<ts>.log`
- watchdog 冷却 600s → 120s
- `KV_CACHE_MEMORY_BYTES` 20GB → 14GB，可用内存约 3.2GiB → 10GiB；KV 仍约 254,491 tokens（1.94×，够单发 128K）
- 恢复每 5 分钟的健康 + smoke

当天验证：health 200，端到端 `FIXED_OK`。偶发退出的 kernel 级根因没有在那次日志里钉死。

## 5. 和推理框架直接相关的结论

1. **换框架的原因是 NIM 长上下文 kernel 崩溃，不是双机网络。** 证据是 `sparse_mla_sm120_prefill.cu:67`，约 40K abort；24K 及以下 NIM 可以过。vLLM pinned 运行时把 40K/64K 做成 0 crash，并把 1K/8K decode 提到约 2 倍。
2. **vLLM 没有取消长上下文风险，只是把可用边界从约 32K 推到 64K，并在 128K 附近留下新的失败模式。** 09-02 的 cuBLAS GEMM 和 09-10 的 `sample_tokens` 超时，都是大 prefill，不是 NIM 那个 SM120 文件的原样复发。
3. **双机不可用有一半是 RoCE GID，不是推理 kernel。** 物理链路正常时，空 GID index 会让 NCCL 在 INIT→RTR 失败。index 会漂，而且两机可以漂得不一样。启动前要用 sysfs 核对「RoCEv2 + IPv4-mapped」那一格，再写 `NCCL_IB_GID_INDEX`。
4. **`/v1/models` 或网关 200 不能代表推理可用。** 09-02、09-10 都是模型列表正常、chat 500 或后端根本没监听。容器 `restart=no` 加上错误的 watchdog 路径，会把一次引擎退出变成持续故障。
5. **GB10 统一内存余量是稳定性条件。** 桌面环境会占内存；`nvidia-smi` 上 Memory N/A、GPU-Util 很高可以只是 GNOME，不能当成推理负载。09-10 把 KV 预留下调、腾出约 10GiB 后，才有继续跑 128K 的内存余量。

## 6. 仍开放、需要厂商或镜像方继续看的点

| 项 | 现状 | 希望确认 |
|---|---|---|
| NIM `sparse_mla_sm120_prefill.cu:67` | 已用换运行时绕开，NIM 容器按手册已停用 | SM121 上该 kernel 是否有后续 NIM 修复；`operation not permitted` 的触发条件 |
| vLLM r16 近 128K prefill | 40K/64K 验收通过；贴近 128K 出现 cuBLAS internal error 与偶发 `sample_tokens` 超时 | `pinned-676a1c89` 是否有更新 digest；128K 的支持声明 |
| 在线 Triton JIT | 崩溃前出现 warmup 未覆盖的 `_gather_shared_paged_supertile_kernel` | 是否应在镜像内补 warmup，避免首个大 shape 边编译边算 |
| GID 布局 | 09-02 两机 index 4；09-10 工作站仍是 3、Node1 是 4 | 驱动升级时 GID 表是否保证稳定；推荐的探测方式是否就是 sysfs |
| 健康检查 | 引擎退出是干净的 exit 0，HTTP 模型列表可以仍是 200 | 官方建议用什么信号判断 EngineCore 真的能生成 |

现网已经在用的缓解：125K 输入硬顶、KV 预留下调、崩溃日志先落盘、watchdog 冷却 120 秒、Node1 compose 目录写对、GID 按节点分别配置。这些是运维兜底，不是 kernel 修复。
