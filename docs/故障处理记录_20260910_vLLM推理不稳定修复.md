# 故障处理记录：vLLM 推理不稳定 / 大规模请求失败

> 日期：2026-09-10（晚）
> 集群：工作站 `cube-f22b`（rank0+LiteLLM） + Node1 `cube-0137`（rank1）
> 现象：模型推理不稳定，大规模请求失败（连续 500）

---

## 1. 现象

- 客户端在 `06:01:59–06:04:14` 连续 6 次 `POST /v1/chat/completions` → **500**。
- 期间 vLLM 后端不可用；模型随后自动恢复。

## 3. 根因分析

| 层面 | 结论 |
|---|---|
| **直接原因** | rank0（vLLM 引擎）**异常退出**，容器挂掉；watchdog 约 2 分钟后才重启（含加载），期间 LiteLLM 全部 500。exitCode=0 的"干净退出"与 2026-09-02 记录一致：大请求触发 `sample_tokens` RPC 超时 → **EngineDeadError → 引擎干净退出**（该 pinned build 的大请求/prefill 稳定性缺陷）。 |
| **放大因素** | ① 内存余量极低（~3–5 GiB），大请求的瞬时内存使其更易触发；② watchdog 冷却 **600s**，停机时间可达 ~10 分钟；③ `compose down` 重启会**删除崩溃容器日志**，无法定位栈；④ soak 监控 02:30 停止，未及时发现。 |
| **已排除** | 内核 OOM Killer（dmesg 无记录）、GPU Xid/驱动错误、GID/NCCL 问题（本次启动正常）、125K 硬顶（工作正常，超限返回 400）。 |
| **复现** | 单发小请求、以及单发 **113K tokens** 大请求**均成功**（68s）→ 说明并非必然崩溃，属偶发，需保留崩溃现场才能最终定位。 |

## 4. 修正措施（已实施并验证）

| # | 措施 | 说明 |
|---|---|---|
| 1 | **崩溃日志保全** | `~/ops/watchdog-vllm.sh` 在 `compose down` 前执行 `docker logs $CTR > ~/logs/vllm-crash-<ts>.log`（备份 `watchdog-vllm.sh.bak-crashlog-*`）|
| 2 | **缩短冷却** | watchdog `COOLDOWN: 600 → 120`（备份 `*.bak-cooldown-*`），停机时间 ~2min |
| 3 | **降低 KV 预留腾内存** | 双机 `.env.canary128`：`KV_CACHE_MEMORY_BYTES: 20000000000 → 14000000000`（备份 `*.bak-kv-*`）；可用内存 **3.2 → 10 GiB**；KV 仍 **254,491 tokens = 1.94×**（足以单发 128K）|
| 4 | **恢复 soak 监控** | 重启 `~/soak_probe.sh`（每 5min 健康+smoke），新日志 `~/logs/soak-20260910-0625.log` |

## 5. 后续（若再复现）

1. **查看崩溃栈**：下次崩溃会生成 `~/logs/vllm-crash-*.log` → 据栈定位（`sample_tokens` 超时 / CUDA OOM / cuBLAS 等）。
2. 若确认为大 prefill 缺陷：可将 `litellm_hooks.py` 的 `HARD_INPUT_LIMIT`（125000）下调（如 96000），或切换 **canary64**（`MAX_MODEL_LEN=65536`）规避。
3. 必要时对镜像方（liquidgravityai / `pinned-676a1c89`）提工单。
4. 关注新增内存余量（现 ~10GiB）是否足够；如仍紧张，进一步下调 KV 或清理工作站桌面负载（gnome/firefox）。
