## 1. 项目简介

本项目在**两台 NVIDIA DGX Spark（GB10）**上部署了 DeepSeek-V4-Flash-0731 大模型，组成一套 **双机推理集群**，通过 **OpenAI 兼容 API** 对外提供服务。

### 核心目标
- 用 2 台单机 DGX Spark 的算力 + 内存拼出一个可跑的 155G/Fp8 模型实例。
- 支持长上下文（NIM 端 32K 基线；vLLM 端稳定到 **64K**）。
- 提供低成本自托管 LLM 推理，可接入 Cursor / OpenCode / LiteLLM / Open WebUI 等上层应用。

### 关键能力一览

| 项 | 说明 |
|---|---|
| 模型 | `deepseek-ai/DeepSeek-V4-Flash-0731`（155G safetensors / fp8） |
| 双机拓扑 | 2× DGX Spark GB10，ConnectX-7 / RoCE 200Gb 直连 |
| 运行时 | NIM 1.11.0-variant（基线）/ vLLM 0.26.1（迁移，推荐） |
| 典型吞吐 | vLLM 1K 场景 ~47 tps（NIM 2.4x），64K 稳定 0 crash |
| 管理 API | `http://172.19.9.104:8000/v1`（NIM 回滚）/ `:18090/v1`（vLLM） |

## 2. 快速开始

### 2.1 最简调用（Python + openai）
```python
from openai import OpenAI

client = OpenAI(
    base_url="http://172.19.9.104:8000/v1",  # 或 18090/v1（vLLM）
    api_key="none",                            # NIM 不强制校验
)
resp = client.chat.completions.create(
    model="deepseek-ai/DeepSeek-V4-Flash-0731",  # vLLM 用 "deepseek-v4-flash-0731"
    messages=[{"role": "user", "content": "你好"}],
)
print(resp.choices[0].message.content)
```

## 3. 架构与运行原理

### 3.1 双机拓扑

```
                       管理网络 / API
                            │
                     172.19.9.104:8000  (NIM) 或 :18090 (vLLM)
                            │
                  ┌─────────▼──────────┐
                  │ Node 0 cube-f22b  │  Rank 0 / API Server
                  │ DGX Spark GB10     │
                  │ 121 GiB 统一内存     │
                  └─────────┬──────────┘
                            │  ConnectX-7 / RoCE 200Gb
                            │  enp1s0f1np1  192.168.100.10 ↔ .11
                  ┌─────────▼──────────┐
                  │ Node 1 cube-0137   │  Rank 1 / Worker
                  │ DGX Spark GB10     │
                  │ 119 GiB 统一内存     │
                  └────────────────────┘
```

| 角色 | 主机名 | 管理 IP | 直连 IP | SSH 用户 |
|---|---|---|---|---|
| Node 0 / Rank 0 / API | cube-f22b | 172.19.9.104 | 192.168.100.10 | winbot（旧 Node0 dgxdeploy 已退役） |
| Node 1 / Rank 1 | cube-0137 | 172.19.49.159 | 192.168.100.11 | dgxdeploy |

### 3.2 推理数据流

1. 客户端请求打到 **Node 0** 的 API Server。
2. 模型权重按 **TP=2 张量并行** 分片到两台机器（各持约 77.5G）。
3. 中间激活经 **CX-7 / RoCE**（数据面）与 **管理网**（bootstrap）在双机间同步。
4. 首次请求会触发 SGLang/vLLM 的 **autotuning**，冷启动较慢，之后提速。

### 3.3 双运行时（NIM vs vLLM）

- **NIM（:8000）**：官方基线，曾经在 >32K 上下文触发 `sparse_mla_sm120_prefill.cu` CUDA crash。
- **vLLM（:18090）**：迁移目标，40K/64K 稳定，吞吐提升约 2 倍。**生产推荐。**
- 两者各自独立的 `docker compose`，互不占用相同端口（见 §9）。

## 5. 日常使用

### 5.1 启动 / 停止（NIM）
```bash
# 启动顺序：先 Rank 0 后 Rank 1
ssh ... dgxdeploy@172.19.9.104 'docker start deepseek-v4-rank0'
ssh ... dgxdeploy@172.19.49.159 'docker start deepseek-v4-rank1'

# 重启
ssh ... dgxdeploy@172.19.9.104 'docker restart deepseek-v4-rank0'
ssh ... dgxdeploy@172.19.49.159 'docker restart deepseek-v4-rank1'

# 停止（用仓库脚本，可到 Node0 ~/deepseek-v4-cluster/scripts/ 下）
bash ~/deepseek-v4-cluster/scripts/10-stop-cluster.sh
```

### 5.2 vLLM 启动 / 停止
```bash
# 启动
cd ~/deepseek-v4-vllm/upstream && docker compose --env-file .env.canary64 up -d
# 停止
cd ~/deepseek-v4-vllm/upstream && docker compose --env-file .env.canary64 down
```

### 5.3 查看日志
```bash
# NIM
ssh ... dgxdeploy@172.19.9.104 'docker logs -f deepseek-v4-rank0'
ssh ... dgxdeploy@172.19.49.159 'docker logs -f deepseek-v4-rank1'
```

### 5.4 接入上层应用
- **LiteLLM**：proxy → `http://172.19.9.104:18090/v1`
- **Open WebUI / Cursor / OpenCode**：把 base_url 指到上述地址，`api_key` 任意。

## 6. 运维手册

> 完整细节见 `deepseek-v4-flash-dual-dgx/HANDOVER.md` §5，此处为速查。

### 6.1 常用命令速查

| 目标 | 命令 |
|---|---|
| API 健康 | `curl -s http://172.19.9.104:8000/v1/models` |
| 双机容器 | `docker ps \| grep deepseek-v4`（两台各跑） |
| 日志 | `docker logs -f deepseek-v4-rank0/rank1` |
| 网络流量验证 | CX-7 数据面有 RX/TX 即正常 |
| 回滚网络 | `bash 11-rollback-network.sh` |

### 6.2 关键环境变量（NIM 容器）
- `NCCL_SOCKET_IFNAME / GLOO_SOCKET_IFNAME = enp1s0f0np0`（CX-7 直连口）
- `HTTP_PROXY / HTTPS_PROXY`：Node0 `127.0.0.1:7897`（Clash）；Node1 `127.0.0.1:7890`（FlClash）
- `NO_PROXY` 含 `xfiles.ngc.nvidia.com`（权重直连，避开封锁）
- `NIM_PRIMARY_NODE=192.168.100.10` / `NIM_NODE_MANAGER_PORT=20000`（仅 Rank 1）

### 6.3 系统级改动（不可覆盖丢失）
- **网络**：`/etc/netplan/40-cx7-deepseek.yaml`（双机 CX-7 直连），备份在 `/var/backups/deepseek-v4/`
- **Docker**：`nvidia-ctk runtime configure --runtime=docker`；`/etc/systemd/system/docker.service.d/http-proxy.conf`
- **8000 端口**：已被 NIM 占用；**Portainer 重装勿再映射 8000**（UI 在 9000/9443）

## 7. 故障排查

> 详细历史见 `HANDOVER.md` §6，此处列最常见 5 条。

### 7.1 NGC 中国区封锁（HTTP 451）
- `api.ngc.nvidia.com`（manifest/配置）必须走**非中国出口代理**。
- 权重 `xfiles.ngc.nvidia.com` 走**直连**，务必在 `NO_PROXY` 中，勿经代理。

### 7.2 容器崩溃循环
manifest 抓取抖动导致。确认设置了：
```bash
NIM_MANIFEST_DOWNLOAD_MAX_RETRY_COUNT=300
NIM_MANIFEST_DOWNLOAD_WAIT_INTERVAL_MS=3000
```

### 7.3 缓存目录权限错（Permission denied (os error 13)）
NIM 容器用 `nvs`(uid 1000) 运行，缓存目录须属 `1000:1000`：
```bash
sudo chown -R 1000:1000 /opt/deepseek-v4/nim-cache
```

### 7.4 端口 8000 冲突
Node 0 原 Portainer 占用。若被重装，**不要再映射 8000**。

### 7.5 Node 0 Clash(7897) 失效
```bash
sudo pkill verge-mihomo   # 会自动被 clash-verge-service 重新拉起
```

## 8. 性能与基准

### 8.1 NIM 基线（warmup 前，含首次 autotuning）
| 场景 | 端到端 | 吞吐 |
|---|---|---|
| 1K prompt / 256 out / c1 | 8.9 s | 14.4 tps |
| 8K prompt / 512 out / c1 | 24.4 s | 8.4 tps |
| 32K prompt / 1024 out / c1 | 20.8 s | 6.5 tps |
| 并发 2（2K/256） | — | 22.4 tps |
| 并发 4（2K/256） | — | 34.0 tps |

### 8.2 vLLM vs NIM（decode tok/s）
| 场景 | NIM | vLLM | 提升 |
|---|---|---|---|
| 1K | 19.6 | **47.3** | 2.4x |
| 8K | 21.9 | **43.1** | 2.0x |
| TTFT | 0.26-0.40s | 0.28-0.41s | 持平 |

### 8.3 长上下文（vLLM）
- 8K~64K 全通过（3/3）。
- 真 64K actual-token（61509 tokens）3/3 通过。
- Prefix Cache：64K 共享前缀 TTFT **16.7s → 0.7s（改善 95.8%）**。

> 一次部署完成 benchmark 为基线；如需精确数字请先 warmup 再测。

## 9. vLLM 迁移（推荐生产路线）

> 详细见 `reports/vllm-migration-report.md`。

### 9.1 为什么迁移
NIM 1.11.0-variant 的 P0：>32K prompt 触发 `sparse_mla_sm120_prefill.cu` CUDA crash。vLLM 迁移解决了该问题并翻倍吞吐。

### 9.2 关键配置（pinned）
| 项 | 值 |
|---|---|
| Runtime digest | `ghcr.io/liquidgravityai/2x-dgx-spark-deepseek-v4-flash-0731@sha256:676a1c89...` |
| 本地 tag | `pinned-676a1c89`（arm64） |
| 模型 revision | `9e165c30...`（与 NIM 缓存一致，直接复用） |
| vLLM 版本 | 0.26.1rc0 + dspark.r16 + FlashInfer + CUDA 13.2 |
| 关键参数 | MAX_MODEL_LEN=65536、TP=2、nnodes=2、prefix caching、DSpark(spec=5) |

### 9.3 回滚到 NIM（容器未删除）
```bash
cd ~/deepseek-v4-vllm/upstream && docker compose --env-file .env.canary64 down
docker start deepseek-v4-rank0   # Node 0，等 API 就绪
docker start deepseek-v4-rank1   # Node 1
curl -f http://172.19.9.104:8000/v1/models
```

## 10. 扩展与开发

### 10.1 如何新增能力
- **性能调优**：在 `~/.env.canary64` 中调整 `MAX_MODEL_LEN`、KV cache、chunked prefill、MoE 通信参数。
- **更多并发**：调整并发连接数，重新跑 benchmark 建立基线。
- **接入工具链**：通过 LiteLLM 做统一网关（路由 / 配额 / 多模型），Cursor / OpenCode 指到网关即可。
- **监控**：建议为 Node 0 Clash(7897) 加存活检测；为双机加 RDMA/NCCL 流量监控。

### 10.2 开发约定
- 所有脚本在本仓库 `scripts/` 有副本，改动后**双机同步**并回写本仓库。
- 新增配置/脚本/报告请放在对应目录并更新本手册 §4 目录说明。
- 敏感信息（NGC Key、SSH 密码）**不入库**，另存于操作者处。
