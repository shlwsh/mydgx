# 工作站客户端与运行环境修复方案 v1.0

适用主机：本机工作站 `cube-fe5e`（NODE123，Ubuntu 24.04.4，aarch64，GNOME 46 / X11）
本文整合三件相互独立的客户端/环境问题：Chromium snap 无法联网、Cursor 无法输入中文、`dsh` 与 `DEEPSEEK_BASE_URL` 的配置冲突。

| # | 问题 | 一句话根因 | 当前状态 |
|---|---|---|---|
| 1 | Chromium（snap）访问任何网站都 `ERR_ACCESS_DENIED` | snapd 自带 `apparmor_parser` 5.0.2 生成的策略在 6.17 内核上触发 AppArmor 网络中介缺陷 | 已用 systemd 单元临时修复，仍待升级内核彻底解决 |
| 2 | Cursor 内无法使用中文输入法 | Electron 启动时未继承 IBus 环境变量，且未开启同步模式 | 已通过桌面项 `Exec` 注入环境变量修复 |
| 3 | 在项目目录内启动 `dsh` 直接报错 | `DEEPSEEK_BASE_URL` 是 dsh 的 bootstrap-only 变量，不能出现在仓库 `.env` 中 | 已在 `.env.example` 明确规范 |

## 一、Chromium（snap）无法访问外网

### 1.1 现象

- snap 版 Chromium（`156.0.8078.47`，rev 3572）访问**任何**网址都报 `net::ERR_ACCESS_DENIED`，包括本地 HTTP 地址。
- 同机 deb 版 Google Chrome 访问外网正常。

### 1.2 影响面

| 应用 | 安装形态 | 是否受影响 | 原因 |
|---|---|---|---|
| Chromium | snap | 是 | 使用 snap 提供的 `snap.chromium.chromium` AppArmor 配置 |
| Google Chrome | deb | 否 | 不使用 snap 的 AppArmor 配置 |
| 其他 snap 应用 | snap | 取决于是否启用网络中介策略 | 同源问题，可按同样方式检查 |

### 1.3 根因

snapd 2.78 自带的 `apparmor_parser` 5.0.2 生成的 `snap.chromium.chromium` 配置，在内核 `6.17.0-1021-nvidia` 上触发 **AppArmor 细粒度网络中介缺陷**：TCP 连接已建立，但对已建立套接字的 `read/receive` 被错误拒绝。

内核审计日志特征：

```text
apparmor="DENIED" operation="file_perm" class="net"
profile="snap.chromium.chromium" comm="Chrome_ChildIOT"
family="inet" sock_type="stream" protocol=6
requested="receive" denied="receive"
```

上游问题：Launchpad `#2169038`、`#2169750`、`#2169328`；修复提交 `apparmor: fix fine grained inet mediation sock_file_perm` 已进入 `6.17.0-1032+` 与 `7.0.0-1025+`。

### 1.4 诊断命令

```bash
# 1) 版本对照
snap list chromium
snap version                       # 观察 snapd 版本
/usr/sbin/apparmor_parser --version   # 系统自带 4.0.1；snapd 内部为 5.0.2
uname -r

# 2) 是否有该 profile 的网络拒绝
sudo journalctl -k --no-pager | grep -E 'apparmor="DENIED".*class="net"' | grep chromium | tail -5

# 3) 当前 profile 由哪个 parser 编译（修复后会以内核兼容格式重载）
sudo aa-status | grep -i chromium
```

> 排除干扰：内核日志里另有一类 `profile="cursor_sandbox" ... sock_type="raw"` 的拒绝，是 Cursor 自身沙箱禁止原始套接字（ping），与本问题无关。

### 1.5 临时修复（当前生效）

用系统自带 `apparmor_parser` 4.0.1 重新编译并加载 snap 的 Chromium 配置：

```bash
sudo apparmor_parser -r -K /var/lib/snapd/apparmor/profiles/snap.chromium.chromium
```

为了避免重启或 snapd 重写配置后再次失效，配置了两个 systemd 单元（本机已启用）：

`/etc/systemd/system/fix-chromium-snap-apparmor.service`

```ini
[Unit]
Description=重载 snap Chromium 的 AppArmor 配置（规避 6.17 内核细粒度网络中介缺陷）
After=snapd.service
ConditionPathExists=/var/lib/snapd/apparmor/profiles/snap.chromium.chromium

[Service]
Type=oneshot
ExecStartPre=/bin/sleep 5
ExecStart=/usr/sbin/apparmor_parser -r -K /var/lib/snapd/apparmor/profiles/snap.chromium.chromium

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/fix-chromium-snap-apparmor.path`

```ini
[Unit]
Description=监听 snap Chromium 的 AppArmor 配置变更并自动修复

[Path]
PathChanged=/var/lib/snapd/apparmor/profiles/snap.chromium.chromium
Unit=fix-chromium-snap-apparmor.service

[Install]
WantedBy=paths.target
```

启用与核查：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now fix-chromium-snap-apparmor.service fix-chromium-snap-apparmor.path

# 现状应类似：service=enabled/inactive（oneshot 已执行完），path=enabled/active
systemctl is-enabled fix-chromium-snap-apparmor.service fix-chromium-snap-apparmor.path
systemctl is-active  fix-chromium-snap-apparmor.service fix-chromium-snap-apparmor.path
```

### 1.6 彻底修复

在维护窗口升级到已修复的内核（二选一），然后重启：

```bash
# 方案 A：继续使用 6.17 NVIDIA HWE 内核
sudo apt-get install linux-image-6.17.0-1032-nvidia \
  linux-modules-6.17.0-1032-nvidia \
  linux-modules-nvidia-580-open-6.17.0-1032-nvidia \
  linux-headers-6.17.0-1032-nvidia \
  linux-modules-nvidia-fs-6.17.0-1032-nvidia

# 方案 B：跟随官方 HWE 元包升级到 7.0（会同时升级 NVIDIA 580.178 用户态驱动）
sudo apt-get install linux-nvidia-hwe-24.04
```

### 1.7 验证

```bash
chromium --headless=new --no-sandbox --disable-gpu \
  --user-data-dir=/tmp/cr-test --dump-dom https://example.com | grep -o "Example Domain"
```

预期输出 `Example Domain`（2026-11-20 实测通过），且 `journalctl -k` 中不再出现 `snap.chromium.chromium` 的 `class="net"` 拒绝。
已经开着的 Chromium 窗口需要刷新页面或重启浏览器才能恢复。

### 1.8 升级内核后清理临时单元

```bash
sudo systemctl disable --now fix-chromium-snap-apparmor.path fix-chromium-snap-apparmor.service
sudo rm /etc/systemd/system/fix-chromium-snap-apparmor.service \
        /etc/systemd/system/fix-chromium-snap-apparmor.path
sudo systemctl daemon-reload
```

### 1.9 注意事项

- 临时单元属于**内核绕过而非修复**：升级内核后务必清理，否则会掩盖后续真实问题。
- `apparmor_parser -r -K` 中的 `-K` 表示按内核兼容模式编译，是关键参数；漏掉 `-K` 可能重现原问题。
- snapd 刷新 Chromium 时会重写 profile 文件，`*.path` 单元负责兜底自动重载。

## 二、Cursor 无法输入中文

### 2.1 现象

在 Cursor（Electron 应用）编辑器内切换输入法无效或无法上屏中文，而系统其他 GTK/Qt 应用正常。

### 2.2 根因

1. Electron/Chromium 启动时**不会自动继承** `GTK_IM_MODULE` / `QT_IM_MODULE` / `XMODIFIERS`（从图形菜单启动时尤其如此）；
2. IBus 与 Chromium 的异步输入通道在部分版本上存在时序问题，需要 `IBUS_ENABLE_SYNC_MODE=1` 强制同步模式。

### 2.3 修复方式：桌面项 `Exec` 注入环境变量

当前 `/usr/share/applications/cursor.desktop`（系统级）与 `~/.local/share/applications/cursor.desktop`（用户级）的 `Exec` 都是：

```ini
Exec=/usr/bin/env GTK_IM_MODULE=ibus QT_IM_MODULE=ibus XMODIFIERS=@im=ibus IBUS_ENABLE_SYNC_MODE=1 /usr/share/cursor/cursor %F
```

`--new-window` 动作同样注入。

为什么同时保留用户级覆盖：**deb 包升级会重写 `/usr/share/applications/cursor.desktop`**，用户级同名文件优先级更高，可保证修复在升级后继续生效。

### 2.4 当前安装形态

| 形态 | 路径 | 说明 |
|---|---|---|
| deb（主用） | `/usr/share/cursor`，包版本 `3.30.14-1794552413` | 当前实际使用；`cursor` 命令在 `/usr/bin/cursor` |
| AppImage 解包（备用） | `~/squashfs-root` | 由 `install/install_cursor_local.py` 安装，便于并行试用新版本 |

AppImage 备用安装（脚本已同步注入 IM 环境变量）：

```bash
cd /home/bot/work/mydgx
.venv/bin/python install/install_cursor_local.py --appimage ~/Downloads/install/Cursor-3.27.12-aarch64.AppImage
.venv/bin/python install/install_cursor_local.py --check
```

### 2.5 验证

1. 从应用菜单启动 Cursor（不要从已打开的窗口内新开）；
2. 在编辑器中按 `Ctrl+Space` 切换到五笔/拼音，输入中文应正常上屏；
3. 若仍异常，从终端启动以确认环境变量已注入：

```bash
/usr/bin/env GTK_IM_MODULE=ibus QT_IM_MODULE=ibus XMODIFIERS=@im=ibus IBUS_ENABLE_SYNC_MODE=1 cursor
```

同时用 `ibus engine` 确认当前引擎（详见《工作站中文输入法与IBus修复方案_v1.0_20261120.md》）。

### 2.6 注意事项

- deb 升级会覆盖系统级桌面项，**用户级覆盖文件是长期保障**，不要删除。
- `IBUS_ENABLE_SYNC_MODE=1` 只影响该应用进程，不会改变全局输入法行为。
- 若冷启动后仍无输入法，优先检查是否从旧窗口内新开进程（继承到不带环境变量的父进程）。

## 三、环境变量约束：`DEEPSEEK_BASE_URL` 与 `dsh`

### 3.1 规则

`DEEPSEEK_BASE_URL` 属于 `dsh`（DeepSeek Harness，本机 `/usr/local/bin/dsh`，`0.2.2-rc.1`）的 **bootstrap-only 变量**，**不得写入本项目 `.env` 或任何仓库内 `.env`**，否则在项目目录内启动 `dsh` 会直接报错。

需要自定义端点时，在启动前临时导出：

```bash
export DEEPSEEK_BASE_URL=https://api.deepseek.com
dsh --profile <name>
```

不设置即使用官方端点。

### 3.2 为什么放在 `.env` 会出问题

本项目的 `.env` 会被工作流脚本自动加载（`python-dotenv` / `env_helper`），而 `dsh` 在 bootstrap 阶段对同名变量有独占要求：一旦发现该变量同时来自环境与仓库 `.env`，会判定配置冲突并中止启动。

### 3.3 已在 `.env.example` 中固化规范

```bash
# ---------- DeepSeek 云端 API（opencode / dsh 使用，双节点共用） ----------
DEEPSEEK_API_KEY=
# 注意：DEEPSEEK_BASE_URL 属于 dsh 的 bootstrap-only 变量，不能写进本 .env 或任何仓库内 .env，
# 否则在项目目录内运行 dsh 会直接报错。需要自定义端点时请在启动前 export：
#   export DEEPSEEK_BASE_URL=https://api.deepseek.com
# 默认不设置即使用官方端点。
```

### 3.4 排查命令

```bash
# 仓库 .env 中不应出现该键（无输出即为正确）
grep -n "^DEEPSEEK_BASE_URL" .env

# 当前 shell 是否临时导出了自定义端点（需要时才应出现）
env | grep DEEPSEEK_BASE_URL

# 确认 dsh 版本与变量读取行为
dsh --version
dsh --help | head -20
```
